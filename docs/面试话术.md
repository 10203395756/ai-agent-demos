## 二、LangChain / LangGraph 核心必问题

### Q1：讲一下LangChain的核心抽象？Chains、Agents、Tools、Memory分别是什么？什么时候用Chains，什么时候用Agent？

**参考答案**：
- Chains是固定流程的流水线，输入输出明确，步骤是提前定死的——适合流程稳定、不需要决策的场景，比如固定的"检索→改写→生成"RAG链。优点是性能稳定、输出可控；缺点是不灵活，遇到没预定义的场景就处理不了。
- Agent是大模型自己做决策，用ReAct/Fuction-Calling等模式动态决定下一步做什么、调用哪个工具——适合场景开放、步骤不确定的任务，比如"帮我查天气再订机票"这种需要自主规划的问题。优点是灵活；缺点是稳定性和成本要额外控制。
- Tools就是Agent可以调用的能力单元，用Pydantic定义参数Schema，有统一的name和description——Agent靠description来判断什么时候调用哪个工具，所以description写得好不好直接影响工具调用准确率。
- Memory是对话历史管理，我自己做的是双层记忆：短期用滑动窗口保留近N轮原文，长期做用户画像持久化，跨会话记忆用户偏好和事实。

**我的经验**：**实际项目里Chains和Agent不是二选一，是组合用的**——RAG核心链路用Chain保性能和可控，外层套Agent处理工具调用和异常分支。纯Agent跑生产不可控，必须有最大迭代次数、超时熔断、人工兜底。

### Q2：LangGraph的StateGraph怎么理解？相比直接用AgentExecutor有什么优势？

**参考答案**（这题是核心，决定你懂不懂LangGraph）：
- LangChain原生的AgentExecutor本质上是个"线性循环"：思考→调工具→观察→思考，直到输出最终答案。它的问题是：**流程固定、不支持分支、不支持并行、不支持持久化断点、没有真正的多人/多Agent协作**。
- LangGraph的核心是**把整个工作流建模成一张有向图**：
  - **State**：所有节点共享的一份状态字典（TypedDict），节点之间靠读写State传递数据
  - **Node**：就是一个个Python函数，接收当前State，返回要更新的State片段
  - **Edge**：定义节点之间的流转，可以是固定边（A→B），也可以是**条件边**（conditional edge）——根据当前State的值动态决定下一个节点是哪个，这就是路由能力
  - **Checkpointer**：把每一步的State都持久化下来，所以天然支持断点续跑、Human-in-the-loop、执行状态查询

**相比AgentExecutor的优势**，对应我项目里的实际收益：
1. **可控的多Agent协作**：Planner→Researcher/Coder/Analyzer→Synthesizer这种多角色分工，原生Agent做不了
2. **Human-in-the-loop**：用interrupt_before可以在任意节点前暂停，等人工输入再继续，我在代码生成、重要决策场景都开了审核
3. **循环和分支原生支持**：可以写"审核不通过→回到执行节点重做"这种回路
4. **可观测性**：每个节点的输入输出都在State里，执行轨迹天然就有，调试和审计方便很多
5. **持久化**：任务跑到一半服务重启了，从Checkpoint恢复继续跑，不用从头开始

**架构师加分点**：LangGraph不是简单的"写代码方便"，它解决的是**生产级智能体的可控性和可靠性问题**——原生Agent跑Demo没问题，到了线上一旦出问题你根本不知道卡在哪一步，LangGraph的状态机让整个流程可观测、可中断、可恢复，这才是企业能用的东西。

### Q3：LangGraph里conditional edges怎么写？Checkpointer机制原理是什么？

**参考答案**：
- conditional edges就是一个Python函数，接收当前State，返回下一个节点的名字（字符串）。比如我项目里写的`route_by_task_type`：根据State里的task_type字段，返回"research_agent"/"coding_agent"/"analysis_agent"/"synthesizer"，LangGraph自动路由。
- Checkpointer原理：每次执行完一个节点，它就把整个State序列化存起来（MemorySaver存内存，生产用SqliteSaver/PostgresSaver），并且给每次执行分配一个thread_id。下次用同一个thread_id调用时，它从上次保存的地方继续。
- interrupt_before/after实现Human-in-the-loop：编译图的时候指定在哪些节点前/后中断，执行到那里时invoke直接返回，State保存下来；等外部拿到人工反馈，用`update_state`把反馈写到State里，再invoke一次就从中断点继续——这个机制非常干净，业务代码里不需要写任何"等待用户输入"的逻辑。

### Q4：讲一下ReAct推理模式？Chain-of-Thought和它有什么区别？

**参考答案**：
- CoT（Chain-of-Thought）是让模型"一步一步想"，把推理过程写出来再给答案，主要提升模型在复杂推理题上的准确率，但它**不会调用外部工具**，纯粹是模型内部推理。
- ReAct = Reasoning + Acting，是"思考→行动→观察"循环：模型先想"我现在有什么信息，还需要什么"，然后决定调用哪个工具（Action），拿到工具返回结果（Observation），再继续思考，循环直到得出结论。
- ReAct的核心价值是把**模型的内部推理和外部工具调用结合起来**，解决了大模型知识截止、不会算数、没有实时信息这些问题。

**项目实践**：我用ReAct做工具智能体，关键是System Prompt里要明确告诉模型：什么时候该调用工具、什么时候直接回答、调用失败怎么处理、最多迭代几次——这些不写清楚，模型会"强行调工具"或者"反复重试同一个工具"。

## 三、RAG核心必问题

### Q5：RAG完整链路有哪些步骤？常见优化点有哪些？

**参考答案**：
完整RAG链路：**文档加载→文档切片→Embedding向量化→存入向量库→用户查询→查询改写→向量检索→重排序→上下文注入Prompt→LLM生成→返回答案**

常见优化点（按我项目里实际做过的讲）：
1. **文档切片**：不要固定长度硬切，要用**语义边界**（我用RecursiveCharacterTextSplitter，按/n/n→/n→。→，逐级切），chunk_size 500字左右、overlap 80字效果最好——太小会丢上下文，太大检索噪音多、Token浪费。
2. **检索优化**：单一向量检索不够，做**混合检索**：向量相似度 + 关键词BM25（我demo里做了简化版关键词加分），然后用Cross-Encoder做重排序，准确率提升很明显。
3. **查询改写**：用户原始问题往往太短太口语，可以先让LLM做Query扩展、HyDE（假设性文档嵌入）、多查询分解——这一步对短Query效果很大，但会多一次LLM调用，需要权衡成本。
4. **上下文压缩**：召回的片段不要全塞进去，做相关度阈值过滤（我设0.3，低于阈值的扔掉）、Token预算控制、冗余去重——上下文不是越长越好，无关内容会让模型"分心"，准确率反而下降。
5. **Metadata过滤**：切片的时候带上source、时间、部门等元数据，检索时先按元数据过滤再做向量搜索，准确率大幅提升。

**量化数据**：我自己项目里，初始版本RAG准确率大概72%，加上切片优化+混合检索+阈值过滤后提升到91%，同时Token消耗因为上下文压缩降了40%。

### Q6：RAG检索不到相关内容/出现幻觉怎么办？

**参考答案**（这题高频，考察落地经验）：
我分三层处理：

**第一层：检索层面解决"找不到"**
- 优化切片策略，chunk_size调小、overlap加大
- 做查询改写/扩展/HyDE
- 混合检索（向量+关键词）+ 重排序
- 适当调大Top-K，同时调高score_threshold，召回更多但过滤更严

**第二层：Prompt层面解决"答错/幻觉"**
- System Prompt里强制要求：**"如果上下文没有相关信息，明确说明知识库中未找到，不要编造"**
- 要求引用来源标注（如[来源1]），这样用户能追溯，也约束模型不乱说
- 降低Temperature（我一般设0.1-0.3），减少模型"自由发挥"

**第三层：兜底机制解决"不可靠"**
- 检索结果为空或score太低，直接返回"知识库暂未覆盖该问题"，不进LLM生成
- 关键场景加人工审核节点（用LangGraph的Human-in-the-loop）
- 对回答做事实一致性校验（用另一个LLM比对回答和上下文是否一致，做自动质检）

**架构师视角**：不要指望"调一个参数解决幻觉"，要在架构上设多层防线——检索层保证召回率、Prompt层约束行为、兜底层保证不出事故。

### Q7：长期记忆怎么设计？短期记忆和长期记忆怎么配合？

**参考答案**：
我做的是**双层记忆架构**：

**短期记忆（会话级）**：
- 就是当前session的对话历史，用滑动窗口控制长度
- 我做了**上下文压缩**：最近6轮对话保留原文，更早的对话用LLM做摘要压缩，只保留关键信息——这样既不会丢重要上下文，也不会让Token爆炸
- 会话结束可以持久化到Redis/数据库

**长期记忆（用户级，跨会话）**：
- 存的是**用户画像**：基本事实（用户是谁、在哪个公司、做什么）、偏好（喜欢什么格式/语言/风格）、关键实体（提到过的项目、产品等）
- 实现方式：每轮对话后让LLM（或规则）从对话中抽取值得长期记住的信息，写入用户Profile存数据库
- 每次对话开始时，把用户Profile摘要注入System Prompt，实现个性化回答

**关键设计点**：
- 长期记忆不是"把所有对话都存下来"——那样检索不到重点、反而污染上下文。要做**结构化的、提炼过的记忆**
- 记忆要有**更新和遗忘机制**：用户偏好变了要覆盖旧记忆，过时的信息要降权或删除
- 可以把记忆本身也向量化，按相关度召回——这叫MemGPT/记忆检索，但复杂度高，初期不用

## 四、工程化 / 稳定性必问题（8年经验重点考察区）

### Q8：大模型接口很慢/容易超时，怎么优化？

**参考答案**（分多层，体现架构能力）：
1. **流式输出（SSE）**：不要等全部生成完再返回，第一个Token出来就开始往前端推，用户感知速度快很多——我项目里所有问答接口都做了SSE，首Token延迟感知从2-3秒降到几百毫秒
2. **提示词缓存**：相同或相似的问题（System Prompt+上下文完全一样）直接缓存结果，我用Redis做，重复问题命中率35%左右，既快又省钱
3. **模型选型路由**：简单问题用小模型（快+便宜），复杂问题才用大模型——做一个路由分类器（甚至可以用规则），成本能降一半以上
4. **并发与异步**：用asyncio异步调用，工具调用可以并行的就并行（LangGraph支持节点并行执行），不要串行等待
5. **超时与降级**：设置合理的超时（流式30秒，非流式10秒），超时后返回"服务繁忙请稍后再试"或走降级模型；调用失败用tenacity做指数退避重试，重试2-3次
6. **连接池**：LLM API用HTTP连接池复用连接，避免每次握手开销

### Q9：Token成本怎么控制？

**参考答案**（这是业务方最关心的问题，架构师必须有方案）：
1. **上下文压缩**：严格控制每次传给LLM的Token数，无关内容砍掉，历史对话做摘要——这是最直接的省钱方式，我做了Token预算控制，每次不超过2000Token
2. **提示词缓存**：相同问题直接命中缓存，不调LLM，零成本
3. **模型分层**：简单任务（分类、改写、提取）用小模型甚至本地模型，复杂任务用大模型
4. **Embedding缓存**：相同文档切片只Embedding一次存向量库，不要每次入库重新算
5. **监控和限额**：Prometheus埋点统计Token消耗，按用户/按接口做配额，异常消耗告警——我埋了LLM_TOKEN_USAGE指标，Grafana上能实时看到每个模型花了多少Token、多少钱
6. **Function Calling代替长Prompt**：很多场景不要把规则全写在System Prompt里，用结构化工具调用代替，省Prompt Token

**量化说法**：上线前后对比，通过缓存+压缩+模型路由，**单轮对话平均Token消耗降低了40-50%**。

### Q10：怎么保证AI服务的高可用？出错了怎么排查？

**参考答案**：
1. **限流熔断**：SlowApi按IP限流，防止恶意流量打挂服务；工具调用失败做熔断，连续失败就暂时停用该工具
2. **重试机制**：网络错误、5xx错误用指数退避重试2-3次；4xx错误（参数错、Key错）不重试直接报错
3. **降级策略**：主模型挂了自动切备用模型；缓存命中时直接返回；非核心功能（如推荐）失败不影响主流程
4. **全链路追踪**：每个请求一个TraceID，从进API到LLM调用到工具调用全程带TraceID打日志，出问题grep一个TraceID就能看到完整链路——排查时间从小时级降到分钟级
5. **结构化日志+监控**：structlog输出JSON格式，ELK采集；Prometheus埋点：请求量、延迟、错误率、Token消耗、工具调用成功率，Grafana看板+告警规则
6. **多副本部署**：Docker+K8s，至少2副本，健康检查自动重启坏实例
7. **灰度发布**：新Prompt/新版本先切10%流量验证，效果好再全量

### Q11：多智能体系统有什么坑？怎么避免？

**参考答案**（体现踩过坑，不是纸上谈兵）：
1. **无限循环**：Agent之间互相踢皮球——必须设置max_iterations（我设5次），超过强制终止返回错误；条件边里要有明确的终止条件
2. **状态冲突**：多个节点同时修改State——State设计要清晰，每个节点只改自己负责的字段；可以加版本号检测冲突
3. **错误扩散**：一个Agent出错，后面所有Agent都基于错误结果继续——每个节点执行完做结果校验，异常时走错误分支而不是继续
4. **成本爆炸**：多Agent意味着多次LLM调用，Token成本是单Agent的2-4倍——必须做缓存、上下文压缩、模型分层
5. **调试困难**：多节点异步执行，出问题不知道卡在哪——LangGraph的State天然解决了这个，每个节点的输入输出都在State里，执行轨迹一目了然；再配合TraceID和日志，调试比原生Agent简单很多
6. **过度设计**：不要什么任务都拆成多Agent——简单任务直接用Chain，复杂任务才上多Agent。我的原则是：从双Agent（规划+执行）开始，确实需要再加专家Agent，不要一开始就上5个10个Agent

## 五、场景设计题（高级岗必考）

### Q12：让你设计一个企业客服智能体，能回答知识库问题、查订单、转人工，你怎么设计？

**参考答案**（用你Demo3的架构直接答）：
我会用LangGraph StateGraph来做，节点大概是：

1. **意图识别节点**：分类用户问题是"知识问答"/"订单查询"/"投诉转人工"/"闲聊"
2. **知识问答分支**：走RAG链检索知识库，生成回答；如果置信度低，直接转人工
3. **订单查询分支**：调用订单查询工具（Function Calling），拿到结果后自然语言组织回答；涉及退款等敏感操作，走Human-in-the-loop让客服确认
4. **转人工节点**：直接把当前对话历史打包，转给人工客服系统
5. **兜底节点**：识别不了的意图，礼貌回复+引导转人工

**记忆设计**：
- 短期：当前会话上下文
- 长期：用户历史订单、VIP等级、之前的投诉记录，从CRM拉取注入Prompt

**工程化**：
- SSE流式输出，客服场景响应速度很重要
- 敏感词过滤、回答合规性校验，避免客服说出不该说的话
- 转人工时，一定要把完整对话历史和AI已经做过的处理一起传过去，不要让用户重复说
- 人工坐席可以看到AI的执行轨迹，知道AI已经查了什么、为什么没解决

**关键机制**：**必须有转人工兜底**——不要追求100%自动化，关键是转人工时体验平滑，不要让用户发火。

### Q13：Function Calling不准怎么办？模型经常选错工具、参数填错怎么解决？

**参考答案**：
1. **工具描述要精准**：description一定要写清楚"什么时候用、什么时候不要用"，最好给1-2个示例——模型靠description选工具，这比什么都重要
2. **参数Schema用Pydantic严格定义**：每个字段加description，必要的字段设为required，枚举字段用Literal限定范围
3. **Few-shot示例**：在System Prompt里给几个"用户问题→正确工具调用"的示例，准确率提升明显
4. **参数校验**：工具函数入口做参数校验，不合理的参数直接返回错误给模型让它重试，而不是让错误参数调用下游
5. **工具数量控制**：一次不要给模型超过5-8个工具，太多了模型会"选择困难"——可以先用一个小模型做工具粗筛，只给大模型相关的工具
6. **错误重试**：工具返回参数错误时，把错误信息返回给模型，让它修正参数重试，设置最多重试2次

### Q15：你对AI智能体未来发展怎么看？

**参考答案**：
短期（1年内）：Agent从"玩具Demo"走向生产落地，核心需求是**可控性、可靠性、成本控制**——这正是工程化能力最值钱的阶段，也是我重点投入的方向。
中期（1-3年）：多模态Agent、端侧Agent会普及，Agent不再是纯文本交互，能看屏幕、点按钮、操作软件，移动端+前端背景的人会有优势。
长期：Agent会成为新的交互入口，但底层框架会收敛，LangGraph这类状态机编排大概率会成为事实标准。

对开发者来说，现在最有价值的不是"会调API"，而是**能垂直某个行业做深度解决方案**——懂AI + 懂行业 + 能落地交付，这种人最稀缺。
